# 01. 全体像と主要メトリクス

## 1.1 パイプラインの 7 ステップ

`kokkai-transcriber/src/pipeline.py` で実装されているパイプラインは以下の 7 段：

| # | ステップ | 主要モジュール | 出力 | モデル |
|---|---------|---------------|------|--------|
| 1 | スクレイピング | `scrapers/shugiin.py` | (in-memory) | — |
| 2 | メタデータ確定 | `scrapers/shugiin.py` | `metadata.json` | — |
| 3 | 音声取得・分割 | `audio/extractor.py` | (一時 WAV) | ffmpeg |
| 4 | Whisper 文字起こし | `transcriber.py` | (in-memory) | `openai/whisper-large-v3-turbo` |
| 4.5 | LLM 校正 | `transcript_corrector.py` | `raw_transcript.json` | `deepseek-ai/DeepSeek-V3.2` |
| 5 | 話者交代検出 | `speaker_tagger.py` | `utterances.json` | `deepseek-ai/DeepSeek-V3.2` |
| 6 | Q&A・要約・トピック・法案タグ | `structurer.py` | `qa_pairs.json` / `summary.json` / `topics.json` | `google/gemma-4-31B-it` |

ステップごとに「LLM が何を任され、どこで失敗するか」のプロファイルが大きく異なる。
全セクションを通じて共通する観察として：

- **Step 4.5（校正）**：LLM の出力が長い・捏造・省略の事故が起きやすい。
  既に `transcript_corrector.py:303-318` で 2 段階の安全網（80% 縮小チェック + 「……」検出）が
  入っており、設計判断としては正しい。
- **Step 5（話者タグ）**：LLM に `splits` 配列だけ返させてコード側で本文を組み立てる方針
  （`speaker_tagger.py:50-64`）が良い。出力が「文番号」だけなのでトークン消費・捏造リスクが低い。
- **Step 6（構造化）**：**ここが最も問題が集中している**。Q&A・要約・トピック・コミットメント・
  関連法案を 2 LLM 呼び出しで返させようとしており、責務が過密。
  `summary.json` と `topics.json` が同一呼び出しから生成されるため、片方が truncation で
  欠落する事故が頻発する（21/140）。

## 1.2 致命傷 Top 5（再掲・データ根拠つき）

### Top 1: Q&A 抽出が「演説／討論／趣旨説明」を扱えていない

**観測**：140 セッション中 22（15.7%）で `qa_pairs.json` が空配列。

```bash
$ find data/shugiin -name "qa_pairs.json" -exec sh -c 'n=$(jq ".pairs | length" "$1"); if [ "$n" = "0" ]; then echo "$1"; fi' _ {} \; | wc -l
22
```

例: `data/shugiin/2026/03/13/56124_本会議/qa_pairs.json`（**坂本予算委員長解任決議案**）。
このセッションは「賛成討論／反対討論」だけで構成されているのに、Step 6 が無理に Q&A を 27 ペア生成し、
**そのうち 21 ペアが answer.full_text="" + evasion_score=1.0**。

```json
{
  "id": "qa_002",
  "topic": "物価高騰対策と予算の組み替え提案",
  "question": { "full_text": "イラン情勢に伴い、原油価格は高騰しており..." },
  "answer": { "full_text": "", "evasion_score": 1.0, "has_commitment": false }
}
```

これがサイト閲覧時の「明らかに失敗」感の最大の原因。詳細は [03-pipeline-architecture.md](03-pipeline-architecture.md)。

### Top 2: 構造化 LLM 呼び出しが truncation で半壊する

**観測**：140 セッション中 21（15%）で `topics.json` の `topics` 配列が空。
ただし同一セッションの `summary.json` の `key_topics` は埋まっている。

例: `data/shugiin/2026/03/03/56092_財務金融委員会`：
- `summary.key_topics`: 5 件（"責任ある積極財政" など）
- `topics.topics`: **0 件**

`structurer.py:665` の `generate_summary_and_topics()` は単一 LLM 呼び出しで
`session_summary` / `key_topics` / `key_commitments` / `topics` / `related_laws` の **5 種を返却**させる。
`max_tokens=8192` の制限と Gemma の出力スタイルの相互作用で、後段（`topics` / `related_laws`）が
落ちる事故が頻発している。

詳細は [07-summary-topics.md](07-summary-topics.md), [11-prompts-and-models.md](11-prompts-and-models.md)。

| 56174_厚生労働委員会 (4/15) | 1 |
| 56189_厚生労働委員会 (4/17) | 2 |
| 56194_厚生労働委員会 (4/21) | 2 |
| 56196_厚生労働委員会 (4/22) | 2 |
| 56209_厚生労働委員会 (4/24) | 2 |

「健康保険法等の一部を改正する法律案」を中心に審議していると `session_summary` 自身が明記している
セッションでも 0〜2 件にとどまる。`laws_compact.txt` を 75 件丸ごと注入しているせいで
LLM が「確信度が低いものは含めない」というプロンプト指示（`structurer.py:122`）に
過度に保守的に従っている。詳細は [09-law-tagging.md](09-law-tagging.md)。

### Top 4: 発言者名の表記揺れが Step 5 出力に持ち込まれている

**観測**：主要閣僚で 4〜5 通りの表記が utterances.json に共存。

| 議員 | 表記バリエーション（utterances 出現回数）|
|------|-----------------------------------------|
| 高市早苗 | 高市早苗(399), 高市内閣総理大臣(21), 高市早苗内閣総理大臣(3), 高市総理大臣(1), 高市(2) |
| 上野賢一郎 | 上野賢一郎(171), 上野厚生労働大臣(126), 上野厚労大臣(2), 上野大臣(2), 上野(3) |
| 赤澤亮正 | 赤澤亮正(179), 赤澤大臣(80), 赤澤経済産業大臣(5), 赤澤国家公安委員長(2)❌, 赤澤防災大臣(1)❌ |
| 茂木敏充 | 茂木敏充(151), 茂木外務大臣(52), 茂木大臣(9), 茂木初等中等教育局長(4)❌ |
| 林芳正 | 林芳正(130), 林総務大臣(33), 林拓海(37)❌, 林鉄兵(7)❌, 林水管理・国土保全局長(5)❌ |

「林」は `_SINGLE_CHAR_SURNAMES = {"林", ...}`（`structurer.py:179`）で 1 文字姓マッチが許可されているが、
**衆議院 221 国会には 林姓の議員が複数いる**。`_fuzzy_lookup`（`structurer.py:182-203`）は
最後にマッチしたものを返す non-deterministic な実装で、この複数 林の取り違えを起こしうる。

❌ 印は明白な事実誤認（赤澤亮正は経産相であって国家公安委員長ではない、茂木敏充は外相であって
初等中等教育局長ではない）。LLM の幻覚が utterances にそのまま入り込み、Q&A 抽出にも
波及している。詳細は [08-name-normalization.md](08-name-normalization.md)。

### Top 5: スクレイパーの委員会名抽出が壊れている

**観測**：5 セッションで `committee="不明"`、4 セッションで `committee="特別委員会"`（具体名欠落）。

`shugiin.py:_extract_session_metadata` は委員会名を 2 段階で探す：
1. `<title>` 内の `[一-鿿]+委員会` パターン
2. ページテキスト内の同パターン

ところが `内閣委員会` のセッション（`56200_不明`）では、ページに `山下貴司(内閣委員長)` と
速記者リンクがあるだけで `内閣委員会` という文字列がページに含まれていない。
正規表現は `内閣委員長` を `委員長` で終わるからマッチさせない（仕様）。
結果として `committee="不明"`、URL に `_不明_56200` のような気持ちの悪いパスが残る。

詳細は [02-cross-cutting-issues.md](02-cross-cutting-issues.md)。

### `evasion_score` 分布（6,308 ペア）

```
0.0-0.1:  284
0.1-0.2: 1387
0.2-0.3: 1703  ← 最多
0.3-0.4: 1111
0.4-0.5:  736

```

**1.0 ちょうどに 249 ペア**集まっており、しかも **その 87%（217 件）は答弁本文 5 字未満**。
0.9〜1.0 の 42 件と合わせても、本来の「完全回避答弁」（例: "個別事件における裁判所の判断について
法務大臣として所感を述べることは差し控えたい"）はごく少数で、大半は **そもそも答弁が無い**
「Q&A ペアじゃないもの」を Q&A ペア化した副産物。詳細は [06-qa-extraction.md](06-qa-extraction.md)。


`speaker_tagger.py:37` のシステムプロンプトは `role` の取りうる値を「委員長 / 質疑者 / 答弁者 /
政府参考人 / 参考人 / その他」の 6 種に限定している。にもかかわらず、LLM は時折
**役職そのもの（〇〇大臣）を `role` フィールドに入れてくる**。31 件と少数だが、Q&A 生成側の
ロジック（`structurer.py:_is_member_of_parliament`）が想定していない値で、サイト側でも
分類エラーになる。詳細は [05-speaker-tagging.md](05-speaker-tagging.md)。
