# 04. 文字起こし品質（Step 4 / 4.5）

## 4.1 設計の良いところ

- **Whisper プロンプトを「直前文脈」として書いている**（`transcriber.py:42-67`）：
  ```python
  _WHISPER_PROMPT_BASE = (
      "第221回国会、衆議院本会議・委員会における質疑応答。"
      "高市早苗内閣総理大臣、木原稔内閣官房長官、..."
  )
  ```
  Whisper の `prompt` 仕様は「指示」ではなく「スタイル模倣のサンプル」なので、これは正しい使い方。
  224 token 制限内で固有名詞をリスト化している点も良い。
- **発言者ごとに WAV をセグメント分割してから Whisper にかけている**（`audio/extractor.py:51-131`）：
  Whisper は 30 秒チャンクで動くので、5〜20 分のセグメントを 1 ファイルとして渡しても内部で
  自動分割される。ただし**話者ターン情報を Whisper API は知らない**ので、セグメント外で発生する
  「他の議員の差し込み発言」（質疑中に大臣が答弁する等）は文字起こしされない。
  → これを Step 5 でカバーする設計だが、後述の通り完全ではない。
- **silenceremove フィルタによるセグメント圧縮**（`extractor.py:90-94`）：
  途中・末尾の 2 秒以上の無音を除去して送信。コスト削減と Whisper 精度の両立で良い。
- **Step 4.5 校正の安全網**（`transcript_corrector.py:303-318`）：
  「……」検出と 80% 縮小チェックは、LLM が省略・要約してしまう失敗を捕捉する正しい設計。

## 4.2 観測されている問題

### A. 固有名詞修正が肝心なところで効かない

ベンチマーク（`benchmark2.log`）の Segment 2 (高階恵美子, 健康保険法質疑) 結果：

```
REF (DeepSeek 真値): "国民の皆様のご理解のもと、国民皆保険制度によって..."
gemma-4-31B-it OUT: "国民の皆様のご理解のもと、介護保険制度によって..."
DeepSeek-V3.2 OUT: "国民の皆様のご理解のもと、介護保険制度によって..."
gpt-oss-120b OUT: "国民の皆様のご理解のもと、介護保険制度によって..."
```

**3 モデルとも「介護保険制度」を残してしまった**。プロンプト
（`transcript_corrector.py:44`）で：

```
3. 同音異義語の修正: 文脈に合わない漢字変換を修正する
   （例: 「介護保険」→文脈が皆保険制度の話なら「国民皆保険」）
```

と明示しているにもかかわらず修正できない。これは **文脈理解の難易度** が高いタスクで、
プロンプト 1 つで解ける問題ではない。

### B. 「個人名 → 役職名」の言い換えが prompt 反映で起きる

ベンチマーク Segment 2:

```
REF: "高階恵美子君。自由民主党の高階恵美子です。"
gemma出力: "高階恵美子君。\n自由民主党の高階恵美子です。"
DeepSeek出力: "高階恵美子君（自由民主党・無所属の会）：\n自由民主党の高階恵美子です。"
```

DeepSeek は **「（所属）」を補完してしまっている**。これはプロンプトに明示した
「発言者リスト」を読んで、出力テキストに追記する挙動。これは：

- 文字起こしの忠実性に反する（実際の発言にない情報を加筆）
- Step 5 の話者タグ付けが「発言者リストにある名前と所属」を期待しているのと衝突しうる

`transcript_corrector.py:113` の禁止事項に
**「発言者の所属名を加筆しない」「発言冒頭に役職を補わない」** を追加すべき。

### C. 短いセグメントでチャンクが 1 つしか出ない

`transcript_corrector.py:_chunk_segment` は CHUNK_CHAR_LIMIT=2000 で whisper_segment を
バンドルする。短いセグメント（200 字程度）では 1 チャンクだけが生成され、並列化の利益はない。
これ自体は問題ないが、**短いセグメントは校正の品質チェック（80% ルール）で**
**誤って棄却されやすい**。50 字 → 38 字のような正常な圧縮が「24% 縮小」と判定される。

例: もし whisper の生テキストが「えー、あの、〇〇についてご答弁申し上げます。」（25 字）で、
LLM が `「〇〇についてご答弁申し上げます。」`（19 字）に校正したとする。比率 76% < 80% で棄却。
**「フィラー除去」を依頼しているのに、フィラー除去後の長さチェックで棄却**するのは矛盾。

改善案: 短いセグメント（< 100 字）では棄却閾値を緩める、もしくは絶対字数差で判定。

### D. `corrected=true` フラグが「全チャンク成功」を意味しない

`transcript_corrector.py:352-357`:

```python
return RawTranscript(
    session_id=raw_transcript.session_id,
    corrected=True,  # ← 一律に true
    corrected_at=...,
    segments=results,
)
```

棄却されたチャンクは `chunk_obj.text`（元テキスト）に置き換わるが、
**外側の RawTranscript は `corrected=true`**。
サイト側からは「校正済みです」とラベルされた未校正テキストが見えてしまう。

改善案：

- セグメント単位で `corrected_chunk_ratio` を持つ
  （成功チャンク数 / 総チャンク数）
- 全体の `corrected_at` だけでなく、`fully_corrected: bool` を追加

### E. Whisper の音声タイムスタンプとセッションのタイムスタンプの整合

`pipeline.py:159-177` で leading silence offset の補正をしているのは正しいが、
**発言者ごとのセグメント分割にはこの補正が反映されない**。
正確には反映されているが、`speakers` のタイムスタンプを書き換えた後に `split_segments` を
呼んでいる（`pipeline.py:178-183`）ので結果的には動いているが、ロジックの可読性が低い。

加えて、**音声長を超えた `start_seconds` は検出されていない**：

```python
# extractor.py:77
end = speakers[i + 1].start_seconds if i + 1 < len(speakers) else total_duration
```

最後の speaker の終端を `total_duration` にする処理は良いが、
途中の speaker の `start_seconds` が `total_duration` を超えていた場合のチェックが無い。
仮にスクレイパーがバグった場合、ffmpeg が「-ss > duration」でエラーかゼロ秒セグメントを
返すが、エラーハンドリングがない。

### F. 同じ発言者が複数回登場するセッションの扱い

衆議院 TV のセッション詳細では、**1 人の発言者が複数回ブロックを持つ**ことがある
（質疑 → 別議題で再登壇）。`scrapers/shugiin.py:_extract_speakers` はそれぞれを別 speaker として
配列に入れる。Step 4 / 5 / 6 でも別 speaker として扱われるので、サイト側で「同じ人」と
集約するには名前マッチングが必要になる。これが
[08-name-normalization.md](08-name-normalization.md) の正規化問題と複合する。

## 4.3 校正の質的観察（実データから）

実際の `raw_transcript.json` を眺めて気づくこと：

- 改行 `\n\n` がほぼ正しく入っている。話者交代が明確な箇所では `〇〇君。\n\n〇〇です。` のように
  整形できている。
- **ただし**、本会議で議長が発言を遮るような場面（不規則発言、「お静かに」等）の改行が
  入らない場合がある。Step 5 の話者交代検出が文単位なので、改行が入らないと
  `_split_sentences` が 1 文として扱ってしまう。
- 法案名や省略表記（「健保法」→「健康保険法」）はかなり良く修正されている。
- ただし**新語・新法案には弱い**：「ヒトゲノム編集胚」のような第 221 回固有の語彙は
  プロンプトに明示しているが、それ以外（議論中に出てきた新しい制度名、人名）は誤認識のまま。
