## 全体感（Executive Summary）

### 良いところ（残したい設計）

- **静的サイト + 構造化 JSON**という土台が効いている。Pagefind で全文検索、Recharts でダッシュボード、フィルタは React 島でクライアント完結。低コストで保守性が高い。
- **出典明示**（衆議院TV / 参議院TV へのリンク）が QA カード・セッションフッタ・グローバルフッタに 3 段で入っており、著作権法 48 条への対応が丁寧。
- **政党カラー**を NHK 選挙報道準拠で揃えたタイムラインは、政治関係者にも違和感が少ない。
- セッション詳細の「発言タイムライン → Q&A → 発言全文」の縦動線は、議論の構造を追いやすい。

### 致命傷（最優先で直すべき）

1. **トピックフィルタの 99.8% が機能不全**。`/browse?topic=...` に渡される「広域トピック」（topics.json の name）と、Q&A レコードが持つ「狭域トピック」（qa_pairs.json の topic）がほぼ別語彙で、フィルタを通すと 0 件になる。ヒートマップの全クリック・ダッシュボード「注目トピック」のチップ・ホームの法案タグ等、トピック起点の導線が**ほぼ全て死んでいる**（詳細: [02-cross-cutting-issues.md](02-cross-cutting-issues.md)）。
2. **「回避度」のメンタルモデルがどこにも書かれていない**。スコアの算出根拠・閾値・サンプルサイズの目安が不在で、一見強い主張（「○○大臣 回避度 90%」）に見えてしまう。法的・社会的リスクが高く、メディアに引用されると損害が出る（詳細: [05-qa-quality-metrics.md](05-qa-quality-metrics.md)）。
3. **ホーム（一覧）／ /browse ／ セッション詳細のフィルタが、別実装で 3 重化**。ご指摘の通り Astro 側 `<script>` と React の FilterPanel が並走しており、URL 設計・状態同期も別。ナビ階層もホームと一覧がほぼ同じ役割を担っている（詳細: [03-information-architecture.md](03-information-architecture.md)）。
4. **モバイルで一覧画面のフィルタが折りたたまれない**（`🔍 フィルタ ▼` トグルが効いていない／開閉ロジックが SSR / hydration とズレている）。スマホ閲覧時はファーストビューがフィルタで埋まる（詳細: [08-mobile-accessibility.md](08-mobile-accessibility.md)）。
5. **発言者分析の 83%（966/1160 名）が `totalAnswers < 5` の超少数サンプル**で、回避度バーが赤一色になり判断材料にならない。委員長や政府参考人も混入しており、本当に追跡したい大臣・副大臣の比較が埋もれる。

### サイト全体への提言（章を跨いだ方向性）

- **「広域トピック」と「狭域トピック」を分離した語彙設計**にする。広域は閲覧導線（カテゴリ）、狭域は検索結果のラベル、の二層構造へ。
- **ホーム = 「最近の論点」要約／/browse = 「全件絞り込み」／検索 = 「全文検索」**と役割を明確化し、サイドバーを共通化したリスト UI を 1 コンポーネントに集約。
- **「回避度」を当面は専門ユーザー向けの "解析ビュー" に隔離**し、一般ユーザーには「明確な答弁／含みのある答弁／論点ずらし」の 3 ラベルとサンプルサイズ表示で出す。閾値・算出ロジックを `/about/methodology` で公開する。
- **ダッシュボードを "国会全体の今" を見るランディング**として再構成し、Tier 0 の入口（ホーム）と統合する選択肢を検討。
- **本格稼働前に "About / 方法論 / 免責事項" ページを必須**とし、運営主体・更新頻度・LLM の限界を明示する。

# 01. ペルソナと利用シナリオ

[← 戻る](README.md)

衆議院本格稼働後を見据えると、想定ユーザーが大きく広がる。
本サイトの UX 判断は「誰がどの瞬間に何を達成したいか」を軸に置く必要がある。

以下、主要 7 ペルソナと、それぞれの 1〜2 個の典型タスク、現状サイトでの詰まり所を列挙する。
（**詰**＝Pain Point、**勝**＝Already Working、**機**＝機会／伸びしろ）

---

## P1. 関心ある一般市民「子育て中の有権者・西田さん（38）」

- **目的**: 自分が支持する／気になる議員が、保育・教育で何を発言したか確かめたい。テレビでは流れない発言を 5 分で読みたい。
- **使い方**: スマホ／通勤の短時間。検索ボックス → 議員名で絞り込み → 要約をスクロール。
- **詰**: モバイルで `/browse` を開くと、フィルタ全部が広がっており（[08 章](08-mobile-accessibility.md)）、結果まで指 3 回スクロール。
- **詰**: 検索結果ラベル `[Q&A]` `[概要]` `[発言]` の意味が分からない。
- **詰**: 「回避度 中（55%）」が何を意味するのか分からず、政治的な印象操作に見える可能性。
- **勝**: Q&A カードが「質問 ─ 答弁」の二段組で、要約が箇条書きで整理されているのは強み。
- **機**: 「この議員をフォロー」（後で更新を確認）が現状ない。

## P2. 政治記者「全国紙・社会部 武田さん（42）」

- **目的**: 直近 1 週間の主要委員会で「○○法案」に絡んだ大臣答弁を漁り、評価が割れる発言や約束事項を抽出する。
- **使い方**: PC、複数タブ。一覧で日付＋大臣＋トピックを絞り、TSV で Excel に流す。
- **詰**: 「関連法案」フィルタはあるが、ホーム・セッション詳細の法案タグからは詳細ページがなく、法案ごとの審議横串が組めない。
- **詰**: TSV エクスポートは便利だが、列定義（CSV ではなく TSV である理由・列名）の説明がなく、Excel で文字化けする可能性。
- **詰**: 「約束トラッカー」の status は常に `unverified`（未確認）固定で、「実際に守られた／約束済み／検討中」の進捗追跡になっていない。
- **勝**: 各 Q&A に動画タイムスタンプ付きリンクがあり、引用するときに直接該当秒へ飛べる。これは商業メディアにとって極めて価値が高い。
- **機**: 「同じ約束を別の委員会で再質問された」トラッキング（議員別ピボット）。

## P3. 国会議員秘書／野党調査チーム「○○議員事務所・佐藤さん（30）」

- **目的**: 自分の議員が次回質疑で使うため、過去 3 ヶ月の閣僚答弁から「論点ずらし」「未回答」のパターンを抽出する。
- **使い方**: PC。発言者で絞り、回避度高をハイライトして全文を確認、出典 URL とタイムスタンプをセットで控える。
- **詰**: 「回避度」の閾値・算出根拠が示されていないので、内部資料に転記しづらい。
- **詰**: 発言者の名寄せが弱い（例: `牧野大臣` と `牧野たかお` が別レコードになりうる）。
- **詰**: 検索結果に `[Q&A]` を多く返したいのに、現状は概要・Q&A・発言が混在する。
- **勝**: Q&A の `commitment_text` が独立フィールドとして抽出されている点は使える。
- **機**: 「議員 A の質問に対する閣僚 B の答弁だけを時系列に並べる」ピボット。

## P4. 政策研究者・大学院生「政策大学院生 林さん（27）」

- **目的**: 「防災庁設置法案」の審議過程を博士論文の事例として集める。発言全文の可検索性、引用の再現性が必要。
- **使い方**: PC。データを CSV/JSON でダウンロードして自前分析。
- **詰**: 一括 JSON / CSV ダウンロードがない（TSV は filter 結果のみ・最大 PAGE_SIZE × フィルタ）。
- **詰**: バージョン情報・更新日時がフッタにもない（dashboard だけにある `lastUpdated`）。
- **詰**: トピック分類が「広域 829 個 vs 狭域 6,286 個」で重複が大きく、カテゴリ集計に使いにくい（[02 章](02-cross-cutting-issues.md)）。
- **機**: API ドキュメント／OpenAPI スキーマ／CC ライセンス明記。

## P5. 海外記者・在京特派員「Reuters 東京支局 Tom さん（45）」

- **目的**: 安全保障・通商の議論を英語で素早く把握。日本語で読むスピードに限界。
- **詰**: UI が完全に日本語のみ。ロゴ・ナビ・委員会名・要約まで全部日本語。Google 翻訳をブラウザに頼ると、Recharts や React 島の動的テキストが翻訳されない。
- **詰**: 委員会名が読めない（"消費者問題特別委員会" 等）。
- **機**: 委員会名・ナビ・主要要約のみでも英語併記すれば、参入障壁が大幅に下がる。

## P6. 高齢市民・スクリーンリーダー利用者「視覚障害者・松本さん（68）」

- **目的**: 関心法案の審議内容を耳で追いたい。動画よりも要約読み上げで効率的。
- **詰**: ヒートマップ・タイムライン SVG に ARIA ラベル／代替テキストがほぼ無い。
- **詰**: チェックボックスは label 付きで OK だが、トグルボタンの状態（`aria-pressed`）が一部欠落。
- **詰**: 配色のコントラスト比は概ね良好だが、回避度の赤・黄・緑は色覚異常者には判別困難。
- **勝**: ボタンがほぼ全て `<button>` 要素になっており、キーボード操作可能。
- **機**: 全文を ARIA `region` でラベル付け、スキップリンクの追加。

## P7. プロダクト運営者・ボランティア開発者「OSS 貢献者・あなた」

- **目的**: 拠出データの整合性を CI で守りつつ、ノイズ（不明委員会・1 件しかない発言者）を後処理で除去したい。
- **詰**: `data/` の Q&A データに `qa.topic`（狭域）と `entry.topics`（広域）が併存し、フィルタ／ヒートマップ／検索が暗黙の前提でぶつかる。
- **詰**: 委員会名 `不明` が混入したまま heatmap に出る。
- **詰**: stats.json の `avgEvasionScore` がサンプルサイズ重み無しの単純平均で、論文・記事に引用されるとリスク。
- **機**: スクリプト `generate-api.ts` に "意味のあるサンプルサイズ" のしきい値を一箇所で持たせるリファクタ。

# 02. 横断的な根本問題（最優先）

[← 戻る](README.md)

このページに載せた問題は、特定の画面ではなく**サイト横断のデータ／用語／挙動の不整合**で、見つけにくいが影響範囲が広い。**P0 級が複数含まれる**。

---

## 2.1【P0】トピックの広域／狭域語彙が分離していて、トピックフィルタが事実上機能しない

### 現象
- `/browse?topic=防災庁の組織機能と権限` を開くと、ヒット 0 件。
- `/dashboard/topics` のヒートマップ（防災庁の組織機能と権限 × 災害対策特別委員会 = 2 件）をクリック → `/browse?topic=防災庁の組織機能と権限&committee=災害対策特別委員会` → 0 件。
- ダッシュボード「注目トピック」のチップ・ホームのキーワードタグから / browse へ飛んでも同じ。

### 根本原因
2 つの「トピック語彙」が存在し、互いにほぼ素集合になっている:

| ソース | フィールド | 性質 | 件数 |
|--------|-----------|------|------|
| `topics.json`（セッション単位）| `topics[].name` | LLM が**セッション全体を要約した広域トピック**（例: 「防災庁の組織機能と権限」）| 829（unique） |
| `qa_pairs.json`（Q&A 単位）| `pair.topic` | LLM が**個別 Q&A に付与した狭域トピック**（例: 「防災庁の勧告権の実効性と運用基準について」）| 6,286（unique） |
| 共通集合 | | | **わずか 10** |

`FilterPanel` の Q&A レベル絞り込み:
```js
const topicFiltered = selectedTopics.length > 0
  ? speakerFiltered.filter((qa) => selectedTopics.includes(qa.topic))
  : speakerFiltered;
```
ここで `selectedTopics`（広域）と `qa.topic`（狭域）が一致しないため、ほぼ常に 0 件。

加えてヒートマップのリンク先（`TopicHeatmap.jsx`）も広域トピックを `?topic=` に渡している:
```js
window.location.href = `${base}/browse?topic=${encodeURIComponent(topic)}&committee=${...}`;
```

### ユーザー影響
- **トピック起点の導線がほぼ全て死んでいる**（ヒートマップ／注目トピック／キーワードタグ／URL 直叩き）
- 「データはあるのに 0 件」という最も信用を失う表示が出る
- 改善前は新規ユーザーの離脱要因 No.1 になり得る

### 改善案
1. **トピック ID を導入**して、広域・狭域に階層関係を持たせる:
   - `topics.json`: `{ id: "topic_001", name: "防災庁の組織機能と権限", related_qa_ids: [...] }` を ID 一次キーで持つ
   - `qa_pairs.json` の `pair.topic` は表示用 short label と、所属する広域 topic ID を `parent_topic_id` で持つ
   - フィルタは `parent_topic_id` で絞る
2. 暫定対応として、**`FilterPanel` のトピック絞り込みを「`entry.topics` に含まれているセッション内の Q&A 全てを返す」に変える**（つまり QA レベルの filter を外す）。これだけでクリック導線が直ぐ繋がる。
3. ヒートマップ → 一覧の遷移時に「related_qa_ids」を URL に積めるなら、`?qa_ids=qa_021,qa_022,...` のような ID リスト指定で確実に当てる手もある。
4. より長期的には、**LLM プロンプト側でトピックタクソノミーを固定**する（例: 「防災・災害」「外交・安保」「経済・財政」… のような上位 30 カテゴリに必ず分類）。

## 2.2【P0】「回避度」の方法論が利用者にも内部関係者にも見えない

詳しくは [05-qa-quality-metrics.md](05-qa-quality-metrics.md) に分離するが、横断的な観点だけ:

- どこにも算出根拠の説明文がない（フッタにも `/about/methodology` のような専用ページもない）。
- LLM の解釈が後から変わると、過去スコアと比較できなくなる（モデル ID は metadata に記録されているが、UI に出ていない）。
- 1 件答弁でも `100%` の表示が成立し、メディアの数字遊びに使われ得る。**法的・社会的に最大のリスク**。

## 2.3【P0】ホーム／一覧／セッション詳細の絞り込みが 3 重に実装されている

詳しくは [03-information-architecture.md](03-information-architecture.md) に。本ページではポイントだけ:

- セッション詳細（`[chamber]/[year]/[month]/[day]/[slug].astro`）の発言者・トピックフィルタは Astro 内 `<script>` で生 JS、URL ハッシュ `#speaker=...&topic=...` で表現。

## 2.4【P1】発言者名の名寄せが弱い（同一人物が複数行に分散）

### 現象（`evasion.json` から）
- `上野賢一郎`（議員名）と `上野厚生労働大臣`（役職名）が別レコード
- 大臣が変わると役職名 alias が分裂（`牧野大臣` ≠ 後任）
- 発言者総数 502 名中、`totalAnswers < 5` が 966 / 1,160 件（評価困難）
- これは Whisper・Speaker tagger の段階で `affiliation` と `name` を別々に持っているのに、`speakers.json` 集計で `name` のみで group by しているのが直因。

### ユーザー影響
- 議員秘書（P3）・記者（P2）の検索で「○○さん」を引いたつもりが半分しか出ない
- 発言者分析の上位ランキングが、現職大臣の役職名 alias で歪む

### 改善案
1. **正規化辞書 `speakers_master.json` を作る**: 議員名・役職名・別表記をまとめた（議員 ID）→ alias 一覧。
2. パイプラインで session 終了後、speaker_tagger の出力に `canonical_speaker_id` を付与。
3. UI 側はこの ID で集計し、表示は「氏名（役職）」に統一。
4. 暫定: `evasion.json` 集計で `totalAnswers < 5` を「サンプル不足」と明示し、棒グラフから除外 or グレーアウト。

## 2.5【P1】「不明」委員会・空文字メタデータがそのまま UI に出る

### 現象
- `topics-heatmap.json` の `committees` に `"不明"` が混入。
- 一部 `metadata.json` の `duration: ""`、`role: ""` 空文字をそのまま表示している。

### 改善案
- `generate-api.ts` 段階で `committee === '不明'` のセッションをヒートマップから除外し、別カウンタとして `unclassified` を出す。
- UI 側で空文字フィールドは表示しない（`{role && <span>...}` パターンを徹底）。
- 委員会名の正規化辞書（`本会議` / `予算委員会` / `特別委員会(○○)` …）を一箇所で管理し、`committee_id` で参照。

## 2.6【P1】SessionCalendar → /browse のクエリ形式が一致していない

### 現象
- `SessionCalendar.jsx` のセルクリックは `?date=2026-04-23` を発行。

### 改善案

# 03. 情報設計とナビゲーション

[← 戻る](README.md)

ご指摘の通り、ホーム・一覧・セッション詳細のフィルタ実装が重複しているのが最大の構造問題。本章はナビゲーション全体・URL 設計・ページ間の役割分担を扱う。

---

## 3.1【P0】「ホーム」「/browse」「セッション詳細フィルタ」の 3 重実装

### 現状の差分

| 画面 | 実装 | 状態管理 | データソース | フィルタ軸 |
|------|------|---------|------------|----------|
| `index.astro`（ホーム）| Astro SSR | なし | `getAllSessions()`（metadata.json 直読み） | 日付グルーピングのみ |
| `browse.astro` → `FilterPanel.jsx` | React 島 (client:load) | URLSearchParams + useState | `/api/index.json` ほか 5 エンドポイント | 院・日付・委員会・政党・発言者・役割・トピック・関連法案 |
| `[chamber]/.../[slug].astro` | Astro + 内部 `<script>` | URL ハッシュ `#speaker=...&topic=...` + DOM 直接操作 | ビルド時 props | 発言者・トピックのみ |

### 何が重複しているか

1. **「Q&A カードを並べて、属性で絞り込み、件数を表示する」**コアロジックが 3 通り。
2. **発言者ボタン／トピックボタン**の見た目（`.speaker-filter-btn`, `.topic-filter-btn`）が、セッション詳細では Astro 側で再実装されている。
3. **URL 管理**が片方クエリ、もう片方ハッシュ。記者が URL を共有するときに混乱する。

### 何が違うべきか
- ホーム = 「最近 N 日の議事カードリスト」（**サマリ閲覧**）
- /browse = 「全件横断のフィルタ＋検索結果」（**深掘り**）
- セッション詳細 = 「1 つの会議の中をスクロール／絞り込み」（**精読**）

特にセッション詳細の「発言者で絞り込む」「トピックで絞り込む」は、ページ内ハイライトに過ぎない。/browse の発言者・トピック絞り込みは、サイト全体から該当 Q&A を引く。**この性質の違いを UI でも見せる**べき。

### 改善案

#### 案 A: フィルタコンポーネントの統合（推奨）
1. `FilterPanel.jsx` を `<QAFeed>` に名前変更し、props で「対象データセット（all / single-session）」と「URL パラメータ前提（query / hash）」を切り替える。
2. セッション詳細では、対象データセットを「このセッションの qa_pairs」に固定して `<QAFeed>` を埋め込む。発言者・トピックボタンのクリック → `<QAFeed>` の state を更新。
3. ホームは `<QAFeed>` の "showFilter=false&groupBy=date" モードで使う（pagination off, 最新 7 日）。
4. 結果: 1 つのコンポーネント、1 つのフィルタ仕様、1 つの URL 設計、1 つのテストでメンテ。

#### 案 B: セッション詳細はそのまま Astro、ただしデザイン共通化
- 共通の `<QACardsLayout>` Astro コンポーネントを作って、見た目は揃える。フィルタロジックは別だが、CSS と機能を一致させる。
- 案 A より低コストだが、長期的には負債が残る。

---

## 3.2【P1】グローバルナビが「最初に何をすべきか」を示していない

### 現状
ヘッダ: `🏛 国会議事録DB ＞ 一覧 ／ 検索 ／ ダッシュボード`

- ホームは独立したリンクが無く、ロゴがホーム遷移を兼ねる。
- 「一覧」「検索」「ダッシュボード」は内容が想像しづらい：初回訪問者は「何の一覧？」「何が違うの？」となる。
- 「ダッシュボード」をクリックするとサブタブが 4 つ（概要／トピック分析／約束トラッカー／発言者分析）。階層が深い。

### 改善案
1. ナビをユーザーが達成したいタスクで命名:
   - 「最新の審議」（旧ホーム）
   - 「絞り込んで読む」（旧 /browse）
   - 「全文検索」（旧 /search）
   - 「全体分析」（旧 /dashboard）
2. ホームにヒーロー領域を 1 つ作り「3 つの入口」を示す:
   - 大きな日付検索ボックス（"2026-04-23 の審議を見る"）
   - 議員名のオートコンプリート
   - 委員会のクイック選択
3. ロゴ脇に「いまの会期: 第 217 回（2026/01/24〜）」など、文脈を表示。

# 04. ダッシュボードが使われていない理由

[← 戻る](README.md)

ご指摘の「ダッシュボードの機能がほとんど使われない」問題について、構造・コンテンツ・心理の 3 面から分析する。

スクリーンショット参照:
- `screenshots/23-dashboard-aboveFold.png`（概要）
- `screenshots/24-dashboard-topics-aboveFold.png`（トピック分析・ヒートマップ）
- `screenshots/25-dashboard-tracker-aboveFold.png`（約束トラッカー）
- `screenshots/26-dashboard-speakers-aboveFold.png`（発言者分析）

---

## 4.1【P0】ランディングとして「次のアクション」が示されていない

### 現状の概要ページ
- **数値カード 4 枚**: セッション数 140 / Q&Aペア 6308 / 発言者 502 / 約束事項 502
- **ナビカード 3 枚**: トピック分析 / 約束トラッカー / 発言者分析
- **月別セッション数バー**
- **52 週カレンダー**
- **最近のセッション 5 件テーブル**
- **注目トピック 10 個**
- 最終更新タイムスタンプ

### 問題

1. **数値の意味が分からない**: 6308 Q&A はどう解釈すれば良いか、新規ユーザーには手がかりがない。「先週比 +120 件」のような変化量が出ていない。
2. **ナビカード 3 枚は上タブと完全重複**: 上のタブ（概要／トピック分析／約束トラッカー／発言者分析）と、ボディ内のカード 3 枚が同じリンク先。タブとカードのどちらでも遷移可能だが、ユーザーは混乱する。
3. **月別バーチャート**: 過去 3 ヶ月分しか積まれておらず、トレンドと言うには情報量が不足。クリックしても何も起きない（ドリルダウン無し）。
4. **カレンダー**: 過去 1 年表示だが、データは 3 ヶ月分しかなく、ほとんどグレー。
5. **最近のセッション 5 件**: ホームと役割が完全に被っている。
6. **注目トピック**: クリックすると `/browse?topic=...` に飛ぶが [02 章](02-cross-cutting-issues.md) の通り 0 件になる。

要するに「眺めるだけで離脱する」ダッシュボードになっている。**何かを発見させる仕掛けが無い**。

### 改善案: 「気付きを与える」ダッシュボードへ

ダッシュボードの存在意義は、フィルタや検索では見えない**鳥瞰**を提供することにある。次の 4 ブロックに再構成する:

1. **今週のハイライト**（自動キュレーション）
   - 「今週最も発言した議員 上位 5 名」
   - 「今週最多のトピック 上位 3 件」
   - 「新たに記録された約束事項 上位 5 件」
   - 各カードはクリックで該当セッション or 議員ページへ
2. **異常値・要注目**
   - 「回避度高 + サンプル十分」な答弁ペア（[05 章](05-qa-quality-metrics.md) の改良版指標で）
   - 「同じ議員が複数委員会で同じ質問」を検出
   - 「閣僚が約束したが、まだ次回質疑が無い」
3. **会期全体の統計**
   - 月別バーは年単位の比較に切り替え、過去会期と並べる
   - カレンダーは半年に縮め、密度を上げる
4. **テーマ別エントリーポイント**
   - 「防災・災害」「外交・安全保障」「経済・財政」など固定分類で章入口

### コンパクト版（短期で出来ること）
- 数値カードに「先週比」「過去 30 日内訳」を併記
- ナビカード 3 枚を削除（タブで足りる）
- 月別バーを「今会期累計」「直近 4 週」の 2 系列に変更

---

## 4.2【P0】トピック分析: ヒートマップが疎すぎて「見るに値しない」

### 現状
- 20 トピック × 23 委員会 = 460 セル中、**非ゼロは 23 セル（5%）**
- 委員会名のヘッダ（縦書き）がスクリーンショット上では切れている／読みにくい
- 「不明」委員会が混入

### 原因
- LLM が**セッション単位で生成する広域トピック名**は session 間で揺れる（同じテーマでも毎回ちょっと違う名前が付く）→ 集計時に bin が増えすぎる
- 上位 20 を取るので、頻度 1〜2 のセルが多くなる

### 改善案
1. **トピックタクソノミーを固定**（[02 章](02-cross-cutting-issues.md) と連動）。「防災・災害」「外交・安全保障」「経済・財政」「社会保障」… の上位 15–25 カテゴリに必ず紐付ける。

3. 委員会も衆議院／参議院でフィルタしたあと、横軸を「Q&A 数 × 平均回避度」のバブルに切り替えるオプション。

# 05. 「回避度」がわからない問題

[← 戻る](README.md)

ご指摘の「回避度の情報がよくわからない」は本サイトの**最も法的・社会的リスクが高いポイント**でもある。本章では、表示・方法論・統計的な妥当性の 3 観点で整理する。

---

## 5.1 現状の表示

### Q&A カード（セッション詳細・/browse 共通）
```
回避度 中（55%）
```
- 数値: `0–1` のスコアを `%` で表示
- ラベル: `< 0.3` → 低（緑）/ `< 0.7` → 中（橙）/ `>= 0.7` → 高（赤）
- 約束あり時: 緑のバー＋「約束: ○○」

### ダッシュボード
- 「平均回避度 0.32」のような数字（概要画面）
- スタックバー: clearCount（緑）/ hedgingCount（黄）/ evasiveCount（赤） の 3 セグメント
- 個別の「明確 / 検討する系 / 回避的」のカテゴリ閾値は表記なし

---

## 5.2【P0】方法論がどこにも書かれていない

### 何が問題か
- 「回避度 = 0–1」が**何を測っているのか**がサイト内に書かれていない
- LLM（DeepSeek V3.2）がどのプロンプトで何を判定しているか、ユーザーに開示されていない
- 同じ答弁を別モデルに評価させたら同じ値になる保証がない（再現性の議論）
- メディアに「○○大臣の回避度 90%」と切り取られたら、訂正できない

### 法的・社会的リスク
- 政治家の発言評価は名誉毀損訴訟に発展する可能性がある領域
- LLM 由来であることを明示しないと、**意見表明と事実陳述の境界が曖昧**になる
- 国会質疑は公開記録だが、「評価」を加えた瞬間に編集著作物になり、責任主体が運営側に移る

### 改善案: methodology ページの新設
**`/about/methodology` を必須**として作る。最低限載せるべき情報:

1. **指標の定義**:
   - 回避度 = 「質問に対する直接回答度合いを LLM が 5 段階で評価し、0–1 に正規化」
   - スケールの意味: 0 = 直接的に回答 / 0.5 = 部分回答もしくは含み / 1 = 質問内容を実質的に回答していない
2. **算出パイプライン**:
   - Whisper large-v3-turbo で文字起こし（精度限界の説明）
   - DeepSeek V3.2 で要約・評価（プロンプト全文を公開）
   - 評価軸の例文を 3 つほど（「明確に答えた例」「論点ずらしの例」「途中で別話題に移った例」）
3. **既知の限界**:
   - 1 質問 1 答弁を前提とするため、同一答弁内で複数論点を含む場合は評価が分散する
   - 質問者の意図を LLM が誤解する可能性
   - 同じ答弁でもモデル変更で値がブレる（再評価で揃える方針）
4. **更新履歴**:
   - LLM モデル ID（`deepseek-ai/DeepSeek-V3.2`）と運用開始日
   - プロンプト変更履歴

UI 側:
- 各 Q&A の回避度バッジに **❓ アイコン**を付け、tooltip で `LLM 自動評価。算出方法 →` リンクを置く
- ダッシュボード上部に「**この指標は LLM 評価値です**」の常時注記を表示

---

## 5.3【P0】「ラベル文言」と「色」のメッセージが過激

### 現状
- 「回避度 高」「回避的」という強い断定語
- 0.7 以上が赤＝危険信号として記号化される
- ダッシュボードのスタックバーで「明確 / 検討する系 / 回避的」の 3 ラベル

### 改善案
- 「回避度」→「**直接回答度**」(逆方向に揃え、高=明確)、もしくは「**論点充足度**」のような中立語
- 「回避的」→「**論点に直接触れていない**」「**検討中・含みのある回答**」
- 色は赤・橙・緑よりも、**青系のグラデーション**にして「色で判断させない」設計
- 評価ラベルを 5 段階に増やし、極端値（0.0 / 1.0）を出にくくする
- 「LLM 評価」を必ず併記

---

## 5.4【P0】サンプルサイズの提示が不十分

### 現状
- ダッシュボード発言者分析: 968/1160 名が `totalAnswers < 5` だが、グラフはまっすぐ全部表示
- `武村展英 totalAnswers=1, evasiveCount=1, avgEvasionScore=1.0` のような行が「100% 回避」になる

### 改善案
1. **しきい値を 2 段階に**:
   - `n < 10`: グラフから除外（「サンプル不足 ○件を非表示」と注釈）
   - `n < 30`: グラフに含めるが、棒の上に `※ n=15` を併記し、棒色を低彩度に
2. **平均回避度の代わりに信頼区間バー**:
   - 棒の上に 95% CI（信頼区間）の小エラーバーを表示
   - サンプルサイズで CI の長さが視覚的に分かる
3. **集計対象の絞り込み**:
   - 委員長は除外（質問・答弁役ではない）
   - 政府参考人と大臣を分けて集計
   - チェックボックスで「大臣のみ」「副大臣以上」「議員質問のみ」を切り替え

## 5.5【P1】Q&A 単体での「コンテキスト」が薄い

1 個の Q&A カードで「回避度 高」と表示しても、**比較対象**が無いと意味を成さない。

### 改善案
- カードに「同じ答弁者の平均回避度」を併記（例: 「この答弁: 0.85 / 平均: 0.32」）
- カードに「同じ法案関連の Q&A 平均」を併記
- 「この答弁の根拠」リンクで、LLM がどこを切り取ったかを `full_text` 上でハイライト

## 5.6【P1】明確／含み／回避の閾値定義が UI から消えている

`FilteredQAList.jsx` のロジック:
- `< 0.3` → 低（緑）／`< 0.7` → 中（橙）／`>= 0.7` → 高（赤）

`generate-api.ts` の `evasion.json` 集計:
- `clearCount`: `< 0.3`
- `hedgingCount`: `0.3 ≤ x < 0.7`
- `evasiveCount`: `>= 0.7`

この閾値はコード固定で UI に出ていない。**論文・記事に引用された場合に、説明責任を果たせない**。

### 改善案
- methodology ページに閾値の根拠（なぜ 0.3 / 0.7 か）を明示
- `evasion.json` 集計時に閾値を出力に焼き込む（バージョニング）
- 将来的にユーザーが閾値を変えてシミュレーションできる UI も検討

---

## 5.7【P2】「約束あり」フラグの基準

`has_commitment` は LLM が判定。緑のコミットメントバーが目を引くので、Q&A カードのデザイン上、回避度よりも「約束」が前面に出る場合がある。

### 改善案
- methodology に「約束の判定基準」を載せる（語尾「努める」「検討する」「実施する」のうちどこから約束扱いか）
- 「努力義務的な約束」と「具体的な行動約束」を 2 段階に分ける
- ダッシュボードの「約束事項数 502」もこの分類で内訳

### 改善案
- 役割を 2 軸に分割:
  - **発言タイプ**: 質問 / 答弁 / その他（合議運営・採決等）
  - **答弁者属性**: 大臣 / 副大臣 / 政務官 / 政府参考人 / 委員長
- AND/OR 切替を明示

## 8.1【P0】モバイルでフィルタが折りたたまれない

### 現状
`FilterPanel.jsx`:
```css
@media (max-width: 767px) {
  .filter-toggle-btn { display: block; }
  .filter-controls { display: none; }
  .filter-controls.open { display: block; }
}
```
- 「🔍 フィルタ ▼」ボタンは表示されている
- しかし、フィルタ本体も**同時に**展開されたまま

### 推測される原因
- 観察時の挙動を見ると、ボタンが出ているのにコントロール部もずっと表示されている
- React 島が `client:load` で読み込まれる前後の SSR/hydration ズレが疑わしい
- もしくは CSS specificity の問題で `.filter-controls` 直下の `display: flex` が `display: none` を上書きしている

### 改善案
1. ロード直後の hydration を待たずに、SSR 時から「mobile == false（デスクトップ前提）」で出力 → CSS で切替
2. CSS を確実に効かせるため、外側 div に `data-filter-open={open}` を付け、属性セレクタで切替:
   ```css
   @media (max-width: 767px) {
     [data-filter-open="false"] .filter-controls { display: none; }
   }
   ```
3. デフォルトの開閉状態をデバイス幅で初期化（`useEffect` 初回で `window.matchMedia('(max-width: 767px)')`）

1. **全ページのフッタに常時注記**:
   ```
   ⚠️ 要約・分類・評価は LLM（DeepSeek V3.2）による自動生成です。
      公式議事録・動画原本を必ず併せてご確認ください。
   ```
2. Q&A カード上部に小さく `[LLM 要約]` バッジ
3. 検索結果カードに同バッジ
4. methodology ページへのリンクを各バッジから

---

## 9.3【P1】出典リンクの粒度

### 現状（良い点）
- セッション詳細上部: 出所 → 衆議院TV
- Q&A カード下部: 出所 → 衆議院TV
- フッタ: 衆議院TV / 参議院TV

### 改善余地
- セッション詳細の出所が小さく薄いグレー → 信頼担保のためにはもう少し目立たせて良い
- Q&A 動画リンクの「該当秒へジャンプ」が中心だが、「動画全体（先頭）」のリンクも添える
- 公式議事録（衆議院議事速報など）が公開され始めたら自動でリンクを足す（過去セッションも遡って）

---

## 9.4【P1】データの更新頻度・遅延の表示

- 現状フッタ／ヘッダに「最終更新」が出ない（ダッシュボード概要のみ）
- 「**○時間前に更新／次回更新は約○時間後**」のような表現があると、サイトが息をしている感じが伝わる

### 改善案
- ヘッダ右上に小さく「直近更新: 6時間前」（hover で正確な時刻）
- ダッシュボード以外のフッタにも `lastUpdated` を表示
- バッチが失敗していたら `データ更新が滞っています` の警告を出す（Healthcheck JSON を `/api/health.json` で生成）

---

## 9.5【P1】訂正・誤字・話者誤判定の報告動線

### 現状
- 「報告する」ボタン・リンク無し
- 誤字（Whisper の誤認識）や話者誤判定（speaker_tagger の誤り）を見つけても、ユーザーは諦めるか SNS で晒すしかない

### 改善案
1. 各 Q&A カード右上に `⋯` メニュー → 「誤りを報告」
2. クリックで GitHub Issue テンプレート or Google Form にプリフィル（セッション ID、Q&A ID、ユーザーが選択したテキストを含む）
3. issue ラベル `correction-request` で分類し、運営側のトリアージ動線へ

## 9.6【P1】ライセンス明示

`ARCH.md` で示唆されている「公的記録のオープン化」コンセプトに対し、ユーザーが**何の条件で再利用できるか**が UI に書かれていない。

### 改善案
- フッタに `データ: CC BY 4.0 ／ コード: MIT` のような明示
- TSV エクスポート時、TSV 先頭にコメント行で出典・ライセンスを焼き込む
- API JSON ファイルのトップに `license`, `attribution` フィールドを足す

## 9.7【P1】LLM モデルバージョンの表示

### 現状
- `metadata.json` に `whisper_model`, `llm_model` が入っている（`deepseek-ai/DeepSeek-V3.2`）
- UI には出ない

### 改善案
- セッション詳細の出所リンクの並びに「処理: Whisper L-v3-turbo / DeepSeek V3.2」を小さく表示
- methodology ページに「モデル変更履歴」を残す
- モデル変更前後で評価値が大きく変わる場合は、UI 側で `※モデル更新により再評価された旧データ` のような注記を出す

## 9.8【P2】記事引用・SNS シェア時の見栄え

[07 章 7.10](07-session-detail.md) と重複。本ページの観点では、**シェアされた先で誤解されない**ことが重要。

### 改善案
- OG image に「LLM 自動要約」を必ず焼き込む

# 10. 拡張機能（Tier 1 含む）

[← 戻る](README.md)

本格稼働のあとに価値を伸ばすための機能候補。
コア体験の P0 / P1 が片付いてから着手する前提で、ペルソナ別に並べる。

---

## 10.1 一般市民（P1）向け

### 10.1.1 「フォロー」機能（ローカル）

- お気に入り議員 / 委員会 / トピックを localStorage に保存
- ホーム上部に「あなたがフォロー中」セクション
- データ更新時、新しい該当セッションがあれば「未読 3 件」バッジ
- 静的サイトでも実装可能（サーバー不要）

### 10.1.2 「読みやすさモード」

- 行間広め・大きめフォント
- ダーク／ライト切り替え（システム連動 + 明示切替）

### 10.1.3 用語ヘルプ

- ホバーで「副大臣とは」「政府参考人とは」のミニヘルプ
- 委員会の役割（"環境委員会で扱うもの"）の 1 行説明

---

## 10.2 政治記者・議員秘書（P2/P3）向け

### 10.2.1 比較ビュー

- 議員 A vs 議員 B: 同じ法案・同じトピックでの発言を並べる
- 委員会 A vs 委員会 B: 同じ法案を扱った 2 つの委員会の質疑差分
- 月別 / 週別の発言量・回避度・コミットメント数の推移

### 10.2.2 法案ページ

- `/laws/:law_id` で法案ごとの審議横串
- 提出から成立までのタイムライン
- 採決結果（賛成・反対）
- 関連 Q&A 全件
- LawEntry に `progression: [proposed, committee, plenary, passed]` を追加

### 10.2.3 同一発言検出

- 議員 A が複数委員会で似た質問を繰り返している
- 答弁者 B が異なる質問者に対して同じ約束を複数回している
- 全文の単純コサイン類似度 + LLM 意味類似度のハイブリッドで実装

### 10.2.4 「約束の追跡」自動化

- 過去の `commitment_text` を時系列で並べ、後の答弁で同じトピックに触れた時に `restated` 候補を提示
- ユーザーが手動で `realized / not_yet` をマーク（GitHub-backed の collaborative editing）

### 10.2.5 議員レーダーチャート

- 議員 1 人につき: 発言量／質問数／約束数／平均回避度／対応大臣バリエーション
- 政党平均との比較を重ねる

---

## 10.3 研究者・データ系（P4/P7）向け

### 10.3.1 公式 API ドキュメント

- 現状の `/api/*.json` は build artefact だが、利用可能な公開エンドポイントとして文書化
- スキーマを `/api/schema.json` で公開
- バージョン管理（`v1`, `v2`）

### 10.3.2 一括ダウンロード

- フィルタ結果ではなく「全データセット zip」を `releases` に毎月公開
- `data-2026-04.zip`（200MB 程度）

### 10.3.3 引用フォーマット

- 各 Q&A に「引用形式コピー」ボタン:
  - APA 風: `衆議院 災害対策特別委員会（2026年4月23日）, Q&A qa_001, 国会議事録リアルタイムDB, 取得日: ...`
  - DOI / ArchiveBox 連携の検討

## 10.4 海外記者（P5）向け

### 10.4.1 機械翻訳済みサマリ

- ビルド時に `summary.session_summary` を英訳
- 委員会名・議員名のローマ字表記
- `/en/...` 配下に並走サイト

### 10.4.2 主要トピックの英語キャッシュ

- 検索ページで `disaster prevention agency` → `防災庁` への自動リダイレクト

## 10.5 Tier 1（BYOK / OpenRouter）

`ARCH.md` Phase 6 に書かれた構想を UI に落とすときの提案。

### 10.5.1 設定画面

  - 「現在のセッション中のみ有効」表示
  - 「お試し用に小モデル」のリンク

### 10.5.2 アンロックされる機能（一例）

- **比較質問**: 「この答弁と先週の答弁を比較して」
- **批評モード**: 「この答弁は質問にどう答えていないか説明して」
- **ユーザー独自の評価軸**: 「経済政策の具体性」「実施期限の明示性」など、ユーザーが評価項目を定義

### 10.5.3 Tier 0/1 の境界の見え方

- キー未設定時はクリックで `/settings` に遷移
